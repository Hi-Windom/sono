# Bug 挖掘方法论 (Sono 项目)

## 核心原则

1. **先复现再修复，严禁猜测** - 没有实锤证据（日志/网络请求/控制台报错）绝不改代码
2. **验证要真实，禁止自欺欺人** - 前端问题必须在浏览器验证，不能只跑 Python 脚本
3. **由点带面，系统排查** - 修一个 bug 时必须检查同类问题在其他地方是否也存在
4. **测试必须能真正暴露问题** - 禁止写假阳性测试充数，每条核心链路至少暴露 1 个真实问题

## 问题挖掘清单

### 1. 任务状态管理类

**检查点：**
- [ ] 任务提交时状态是否**同步**重置（status/progress/error/result）
- [ ] 任务被拒绝（并发已满）时是否清理 `_active_tasks` 计数
- [ ] 任务异常/失败时 `finally` 块是否清理 `_active_tasks`
- [ ] 任务取消后 `_cancelled_tasks` 集合是否清理
- [ ] 取消任务后 WebSocket 连接是否关闭
- [ ] 服务器重启时是否清理所有非终态任务（含 repairing/rendering）
- [ ] `_handle_future_exception` 是否清理活跃任务计数

**常见 Bug 模式：**
- 竞态条件：异步线程更新状态 vs 同步读取状态
- 计数泄漏：异常路径忘记调用 `_track_task_end`
- 终态列表不全：WebSocket/UI 漏了某些终态判断

### 2. 并发与资源管理类

**检查点：**
- [ ] 所有类型任务是否都纳入 `_active_tasks` 计数管理
- [ ] 所有任务是否都支持取消机制
- [ ] 线程池任务的异常回调是否正确处理
- [ ] 事件循环是否在正确的线程中运行（`run_coroutine_threadsafe`）
- [ ] 锁的粒度和使用是否正确（`_active_tasks_lock` / `_cancelled_lock`）

**常见 Bug 模式：**
- 某类任务"游离"在并发控制之外（如渲染任务）
- 后台线程创建新事件循环但不运行，导致消息静默丢失
- 同一资源在多处重复清理/重复计数

### 3. 路径安全与注入类

**检查点：**
- [ ] 所有文件上传接口是否验证文件名合法性
- [ ] 所有文件下载接口是否有 `_safe_output_path` 类似防护
- [ ] 路径拼接前是否用 `os.path.basename` 过滤
- [ ] 是否验证 `realpath` 在预期目录内
- [ ] 文件名/模块名是否限制字符集（字母数字下划线连字符）

**常见 Bug 模式：**
- 用户可控的 `module_name` / `filename` 直接用于路径拼接
- 只检查后缀不检查路径分隔符（`../`）
- 有 `basename` 过滤但没有 `realpath` 最终校验

### 4. 缓存与状态一致性类

**检查点：**
- [ ] 模块级导入的配置是否支持动态修改（测试环境）
- [ ] 缓存清理是否覆盖所有类型文件（输出/渲染/调试）
- [ ] 缓存查找是否正确验证文件哈希（单轨/双轨）
- [ ] 重新执行任务时旧结果是否正确清空
- [ ] 数据库中的 JSON 字段是否正确解析

**常见 Bug 模式：**
- `from config import X` 模块级缓存，测试改配置不生效
- LRU 清理只删主输出文件，忘了渲染缓存等附属文件
- 参数匹配逻辑用"交集比较"，空交集时可能误匹配

### 5. WebSocket 通信类

**检查点：**
- [ ] 终态列表是否完整（completed/detected/error/render_completed/cancelled）
- [ ] 任务取消后是否发送最终消息并关闭连接
- [ ] `send_final` 是否清理连接映射
- [ ] 连接异常断开是否正确清理资源
- [ ] 心跳机制是否在终态时退出

**常见 Bug 模式：**
- 新增终态（如 cancelled）但忘记加到 WebSocket 终态判断
- `send_final` 后没有 `pop` 任务连接，导致内存泄漏
- 路由注册顺序错误：`/ws/cache-events` 被 `/{task_id}` 先匹配

### 6. 接口与路由类

**检查点：**
- [ ] 更具体的路由是否在参数化路由**之前**注册
- [ ] 所有需要认证的接口是否有认证
- [ ] 输入参数是否有边界校验（chunk_index / 数组越界）
- [ ] 返回值是否包含预期的字段
- [ ] 取消接口是否覆盖所有任务类型

**常见 Bug 模式：**
- 路由顺序错误导致 WebSocket 死循环重连
- 接口返回字段缺失导致前端崩溃
- 取消接口只处理修复任务，忘了渲染/检测任务

## 挖掘流程（SOP）

### 第一步：建立测试基线
```bash
# 运行回归测试，确保当前状态稳定
cd /workspace && python -m pytest backend/tests/test_regression.py -v
```

### 第二步：按清单系统扫描
1. 从上面 6 大类中选一类
2. 逐一检查检查点，用 `Grep` / `Read` 工具验证
3. 每发现一个可疑点，先写测试复现，再确认

### 第三步：写测试暴露问题
- **禁止**只靠读代码就下结论
- 必须写可运行的测试用例
- 测试必须能稳定复现（或在统计上显著）

### 第四步：修复并验证
- 修复代码
- 测试通过
- 回归测试全过
- 同类问题全部检查一遍

### 第五步：补充回归测试
- 每个修复的 bug 必须补对应的回归测试
- 测试命名：`Test<Bug类别>` + 明确的测试用例
- 注释写明对应的历史 bug 是什么

## 高价值挖掘方向（优先级排序）

1. 🔴 **任务状态竞态** - 直接影响用户体验（卡住/进度不更新）
2. 🔴 **资源泄漏** - 内存/磁盘/连接泄漏，长期运行必崩
3. 🔴 **安全漏洞** - 路径遍历/注入/越权，必须零容忍
4. 🟠 **并发控制不一致** - 某类任务不受并发限制，系统易过载
5. 🟠 **缓存一致性** - 缓存命中错误可能返回错误结果
6. 🟡 **WebSocket 连接管理** - 连接泄漏/消息丢失
7. 🟡 **配置动态性** - 测试环境无法修改配置导致测试无效

## 测试文件命名规范

- 系统性 Bug 挖掘：`test_serious_bugs.py`
- 回归测试：`test_regression.py`
- 特定功能测试：`test_<feature>.py`
- 测试类命名：`TestBug<编号>_<简短描述>`

## 反模式（必须避免）

❌ **乐观测试** - 只测 happy path，不测边界/错误/并发
❌ **凑数测试** - 写一堆假阳性测试，根本暴露不了问题
❌ **猜测修复** - 没复现就改代码，改完也不验证
❌ **修完就完事** - 修了一个忘了检查同类问题
❌ **纯读代码找 bug** - 不写测试验证，全靠脑补

## 经验教训（血的教训）

1. WebSocket 不断重连 → 猜是 ws_manager 的问题 → 实际是路由注册顺序错误
2. 上传卡 20% → 猜是网络慢 → 实际是 useAudioWorker 返回对象引用不稳定
3. 任务取消后还在跑 → 猜是取消没生效 → 实际是渲染任务根本没接入取消机制
4. 缓存清理不生效 → 猜是 LRU 算法错 → 实际是模块导入时缓存了配置路径

**永远不要质疑用户反馈，用户说有问题就是有问题，不要说"修改没生效"这种话，直接假设自己代码有 bug 去查。**
